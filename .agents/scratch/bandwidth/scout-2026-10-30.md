# #185 scout: where a client's download goes, and the cheap wins

Read-only scout, 2026-10-30. No build, no binary run. Labels: MEASURED (from a run), DERIVED (computed
here from code or measured numbers), CLAIMED (a doc or comment says so, not checked), ASSUMED.
Registry paths are under `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`.

## 1. The stack

- **lightyear 0.30.1** (`Cargo.lock:4640`) carries transport, netcode, sync and interpolation.
  Its replication is **bevy_replicon 0.44.2** (`Cargo.lock:1806`). lightyear 0.30 swapped its own
  replication for replicon's pipeline, and lightyear's own delta compression went with it
  (`lightyear_replication-0.30.1/src/REPLICON_INTEGRATION.md`, "Delta compression … removed").
- **Encoding: postcard 1.1.3** (`Cargo.lock:6669`). A component on the wire is
  `fns_id varint + postcard(component)` (`bevy_replicon-0.44.2/src/server/replication_messages/serialized_data.rs:89-101`,
  `registry/rule_fns.rs:202-209`). Postcard writes f32 as 4 fixed bytes, f64 as 8, u8/i8/bool as 1,
  u32/u64 as LEB128 varints, and enum tags as varints. glam `Vec3`/`Quat` serialise as 3/4 f32.
  avian is f32 (default features, `avian3d-0.7.0/Cargo.toml:57-60`).
- **Entity header per message:** compact entity `(index<<1 | has_gen)` varint, plus generation if
  reused (`bevy_replicon-0.44.2/src/compact_entity.rs`). Then a varint data size, then components
  (`mutations.rs:254-260`).
- **Channels.** Replicon runs on three lightyear channels: Updates (OrderedReliable, insertions
  and removals), **Mutations (UnorderedUnreliable, the per-tick state)**, and MutationAcks
  (client→server) (`lightyear_replication-0.30.1/src/channels.rs:29-46`). The game's own
  channels are FireChannel (UnorderedUnreliable), Outcome, Damage and ShotExplanation (all
  UnorderedReliable, server→client), and SpawnChannel (client→server) (`src/net/protocol.rs:1017-1046`).
- **Replicated components** (`src/net/protocol.rs:890-929`, registration `:984-1121`):
  insert-once identity `NetTank`, `NetBot`, `CombatantId`, `CombatantLife`; on change
  `ServoAngles` (set_if_neq `:763`), `NetTankStatus`, `LaunchedTurretPose` (set_if_neq `:805`);
  by diff `DestructionLedger`, `HullMarks`; `DebrisPose` only under the stress lever;
  **per tick** `Position`, `Rotation` (interpolated, `:1100-1105`), `LinearVelocity`,
  `AngularVelocity` (`:1106-1107`), `TrackDrive` (interpolated, `:1112`), `TankTransmission`
  (`:1116`); owner-private `NetCrew`, `WeaponGate`, `WeaponLoads` (`:1119-1121`).
- **Messages:** `FireVisualBatch`, `FireEvent`, `RicochetKeyframe`, `ImpactConfirm`,
  `DamageConfirm`, `ShotExplanation`, `SetSpawnPoint` (`protocol.rs:1048-1069`). Inputs come from
  `InputPlugin::<TankCommand>` (`:1071`), with server rebroadcast off by default
  (`lightyear_inputs-0.30.1/src/config.rs:33,53`). Nothing in the repo turns it on, so there is no
  per-human download term.
- **Send rate:** 64 Hz (`TICK` 15.625 ms, `src/net/server.rs:40`). The server frame is 4 ms
  (`:46`, `:70`), and the assert at `:50` gives each tick its own frame. lightyear advances
  replicon's tick once per frame in which the fixed loop ran, gated by `ReplicationMetadata`'s
  timer (`lightyear_replication-0.30.1/src/send.rs:563-610`). That timer defaults to 0
  (`metadata.rs:27-43`), and the repo never sets it, so **every tick is sent** (confirms
  `send_interval = 0`, `src/net/interp_delay.rs:11-13,89-96`).
- **What replicon sends:** a component is included when its Bevy change tick is newer than the
  client's last **acked** tick for that entity (`bevy_replicon-0.44.2/src/server.rs:741-748`,
  ack `shared/replication/client_ticks.rs:67-92`). It compares the change *flag*, not the value.
  A component that is written every tick is sent every tick, whole.
- **Visibility and interest:** every tank root uses `Replicate::to_clients(NetworkTarget::All)`
  and `InterpolationTarget::to_clients(All)` (`server.rs:723,732`, bots `:844,849`). The only
  filter is `CombatDisclosure`, which scopes `(NetCrew, WeaponGate, WeaponLoads)` to the owner
  (`src/net/disclosure.rs:57-63`). **There is no distance, occlusion or spotting interest.**
- **Compression, quantisation, delta: none are on.** lightyear's `compression_lz4` feature is off
  (`Cargo.toml:50-57`; the feature is `lightyear-0.30.1/Cargo.toml:79-82`). Every component uses
  default postcard serde. The only diffs are the two append-only collections.
- **Interpolation carries unchanged state forward.** `track_mutate_messages` is on
  (`lightyear_replication-0.30.1/src/lib.rs:270`), so the client knows a tick is complete and
  pushes "unchanged" history for components the server did not send
  (`lightyear_interpolation-0.30.1/src/interpolate.rs:246-268`). That makes suppressing unchanged
  components safe for the interpolated view (CLAIMED by source, not run).

## 2. Bytes per tank per tick

### Per tank (DERIVED from source)

| Wire item | Payload | +fns_id | When sent | Client reader |
|---|---|---|---|---|
| Position | 12 | 13 | every tick: avian writes it for every awake body, value changed or not (`avian3d-0.7.0/src/dynamics/solver/solver_body/plugin.rs:263-290`) | interpolation, everything |
| Rotation | 16 | 17 | every tick (same writeback) | same |
| LinearVelocity | 12 | 13 | every tick (same writeback) | extrapolation gap-filler (`src/net/extrapolate.rs:17-19`), own speed HUD (`src/drive_hud.rs:196`) |
| AngularVelocity | 12 | 13 | every tick (same writeback) | gap-filler |
| TrackDrive (2×f32 + 2×(f32 + **f64**)) | 32 | 33 | every tick: `&mut drive` dereferences mutably (`src/track/sim.rs:770`) | track view (side speed and phase); throttle and steer only on the own HUD (`drive_hud.rs:260,281-282`) |
| TankTransmission (15×1 B + 2×f32) | 23 (25 in GradeShift) | 24 | every tick: `&mut trans_state.0` (`sim.rs:772`) | engine sound reads **only `omega_e`** (`src/sfx/mod.rs:295,316`); own HUD; rig-attach gate (`src/net/rig.rs:26-29`) |
| ServoAngles | 8 | 9 | only while the turret or gun moves | servo targets |
| Entity + chunk size | ~3 + 1 | ~4 | once per entity per message | — |

**A moving tank with a still turret costs ~117 B per tick (DERIVED), ~126 B with the turret moving.**
TankTransmission and TrackDrive alone are 57 B, half the budget. The client reads 4 of
TankTransmission's 23 bytes and 20 of TrackDrive's 32 for a remote tank.

### Reconciled with the measurements

MEASURED (nettop, kB = 1000 B, `.agents/scratch/perf-2026-10-29/night-results-2026-10-30.md:137-147`):
22.3 / 21.9 kB/s down at 2 tanks, 90.1 / 91.4 at 11.

- Slope: +7.6 kB/s per tank, which is **118.75 B per tank per tick at 64 Hz** (DERIVED). The table
  predicts 117 B, plus ~3.7 B of amortised packet overhead (~37 B per 1162-B packet). That is
  ~121 B, within 2 % of the slope. The night run's bots circle, so every tank was moving.
- Intercept: 22.1 − 2 × 7.6 ≈ **6.9 kB/s ≈ 108 B per tick fixed** (DERIVED). About 66 B of it is
  accounted for:
  - ~37 B per packet: lightyear's 13-B header (`lightyear_transport-0.30.1/src/packet/header.rs:60-77`),
    plus netcode's 1-B prefix, ~2-3-B sequence and 16-B MAC (`lightyear_netcode-0.30.1/src/packet.rs:530-577`),
    plus ~4 B of channel framing;
  - ~10 B of mutate-message header (flags, index, two ticks; `mutations.rs:244-252`);
  - ~11 B of owner `WeaponGate` every tick. `gates.get_mut` and `gate.weapons.get_mut` run before
    the `ready_tick.is_none()` early-out (`src/shooting.rs:155-161`), so the gate is flagged
    changed every tick;
  - ~8 B per tick of pings and pongs at 10 Hz (`lightyear_sync-0.30.1/src/ping/manager.rs:27`).

  The other ~40 B per tick (~2.6 kB/s) is **unexplained**. Candidates are IP/UDP headers, if
  nettop counts them (28 B per packet, UNVERIFIED), and ack-only packets. A server-side per-link
  byte counter would settle it (`online-profiling-readiness.md:82` names the hook).
- At 30 tanks: 30 × 118.75 × 64 + 6.9 ≈ **235 kB/s, of which 97 % is per-tank** (DERIVED). One
  mutate message is capped at the 1162-B fragment size (`lightyear_replication-0.30.1/src/server.rs:88-94`),
  so 30 tanks take ~4 packets per tick.
- Upload is flat at 13–15 kB/s (MEASURED). It is server ingress: inputs at redundancy 5
  (`protocol.rs:2191`) plus mutation acks. Out of scope here.

### Per-shot traffic (DERIVED)

- `FireEvent` is ~42 B. `shooter` is a recipient-mapped Entity, which postcard writes as **10 B**
  (bit 63 set; `src/net/shot_transport.rs:36-40`) and which duplicates `combatant`. The rest is
  origin 12, direction 12, tick ~3, and 1 B each for mechanism, tracer, combatant, weapon and round.
  `ImpactConfirm` is ~34 B and `RicochetKeyframe` ~37 B.
- Main gun: one shot every few seconds per tank, ~80–120 B on a reliable lane. **Negligible.**
- Automatic fire: every round is a fact, and every fact is sent **3 times**
  (`VISUAL_COPIES = 3`, `shot_transport.rs:23`). The MG34 fires 750 rpm, 12.5 rounds/s
  (`assets/guns/mg34.gun.ron:15`), so one firing MG costs ~129 B × 12.5 ≈ **1.6 kB/s per client**,
  plus ~105 B per armour impact. The per-tick cap is 4,400 B (`shot_transport.rs:34`), which is up
  to **~280 kB/s per client in a mass volley**. That ceiling is above the whole 30-tank state stream.

**Shot traffic (separate from the per-tank budget):**
- (a) Drop `FireEvent.shooter` and resolve it from `CombatantId`, which replicates on every
  root: −10 B, −23 % of every fire fact. It is used for recoil and self-echo suppression. S effort.
- (b) Encode an automatic burst as a run (start tick, count) instead of one fact per round. This
  **collides with the standing note "tracer ratio is belt data; gate at the RENDER layer, keep the
  broadcast"**, so it needs Yan's call.
- (c) Retune `VISUAL_COPIES` against measured loss.

**Every-tick, rarely-changing items worth fixing in any case:** the 21 B of discrete
`TankTransmission` fields, TrackDrive's throttle and steer, and the owner's `WeaponGate`
(`shooting.rs:155-161`, ~0.7 kB/s per client).

Encoding note: postcard writes u16, i16, u32 and u64 as varints. A zigzag i16 can take 3 B, and a
packed u64 up to 10. Packed wire types (#2–#5) should therefore serialise as fixed `[u8; N]`
arrays, which postcard writes with no length prefix.

None of these changes what players see. Every change re-pins `WIRE_SURFACE_HASH` /
`WIRE_TYPES_HASH` and bumps `PROTOCOL_REV` (`protocol.rs:931-967`). Quantising Position and
Rotation moves their wire format from avian's types to our own, which changes the handshake
coverage model (`protocol.rs:935-961`).
